# @agentproto/reach

## 0.1.0

### Minor Changes

- d1b04e3: One rule for an attachment's name (`attachmentNameOf`, exported from reach): a string, or an object's first non-empty `name`, `filename` or `fileName`. The REACH preview parser and the Telegram approval card now read the job kit's `{ filename, mimeType }` attachments, so the `Files:` line appears.
- 8e5c9a8: New REACH adapter kind `chat-sdk`, in the new optional package `@agentproto/reach-chat-sdk` (Chat SDK `chat`, `@chat-adapter/whatsapp` and `@chat-adapter/state-memory`, all pinned to 4.44.0). First platform: WhatsApp Cloud API, `tell` only, outbound only. A route entry `{ id, kind: "chat-sdk", platform: "whatsapp", to, whatsapp: { phoneNumberId, accessToken }, timeoutMs? }` posts one text (the summary, then each link on its own line, capped at 4096 characters) and answers `delivered`, `deduped`, `undelivered(outside-24h-window)` on Meta error 131047, `failed(maybe-sent)` once the post started, `failed(send-failed)` before it, or `failed(timeout)` (default 10 s). An `ask` answers `undelivered(ask-not-supported)` with no request, so the route goes on to the floor. No token, phone number id, recipient or Meta error text is put in a receipt or a log line.

  `@agentproto/reach` adds `ReachChatSdkRouteEntry` to the `ReachRouteEntry` union. `@agentproto/runtime` accepts the entry in `reach.routes.*`, redacts `whatsapp.accessToken` to `{ set: true }` in `config_get`, lists the package under `optionalDependencies` and imports it only when the owner route names a `chat-sdk` entry (otherwise such an entry is skipped `chat-sdk-not-installed`). A route made only of `chat-sdk` entries cannot acknowledge an approval, so it starts no router and the Telegram bridge keeps announcing on its own.

- af8e0db: New package `@agentproto/reach`, the REACH contract (`reach/v1`) with zero runtime dependency. It has the `ReachMessage`, `ReachReceipt`, `ReachAdapter`, `ReachCapabilities`, `ReachRouteEntry` and `ReachAnswer` types, `reachContentFromPreview` (approval preview to message content), a strict `parseReachReceipt`, and `runReachConformance`, a check a webhook receiver can run in its own tests.

  The daemon gets an opt-in REACH router. With `reach.routes.owner` set, each `approval:requested` becomes one message that goes to the route's adapters in order (`webhook`: a signed POST answered by a receipt; `telegram`: the existing approval card bridge) until one answers `delivered`, `deferred` or `deduped`. Every attempt is appended to the approval's `reach.json`. If no adapter acknowledges, the daemon emits `reach:undelivered` and logs `reach: undelivered <id>`. A watchdog sends any pending approval that has no acknowledgement after 60 s through the last `telegram` entry and logs `reach: MISSING <id>`. A decided or expired approval closes the webhook that acknowledged it. `POST /approvals` and `approval_request` accept `reach: false | { urgency }`, and the MCP tool does not accept `urgency: "now"`. `config_get` never shows the webhook `secret`. Without `reach` config the behaviour is unchanged.
